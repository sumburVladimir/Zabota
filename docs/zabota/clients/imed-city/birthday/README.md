## Что дописать при настройке

1. **Блок «не чаще 1 раза в 180 дней».** В `IN (:DID)` добавить id второй
   версии того же сценария (с фильтром по Шорстову ↔ общий). Иначе пациенты
   Шорстова получат два поздравления в один день: строк в брифе шесть, а
   пар «одно и то же поздравление» — три.
2. **`:IPAT`.** Если в параметрах сценария его нет — заменить `TOP (:IPAT)`
   на `TOP 7` (обычное ограничение отправки за прогон) или завести параметр.
3. **Расписание.** У первых трёх строк бриф время не задаёт
   («соответствует общему времени работы отправок»); у 4-6 — 11:05 / 10:55 /
   11:20, каждый день, один раз в день.

## Принятые трактовки

- «Визит действительный» = `ISNULL(Visit_state,'N') <> 'C'`
  (в базе: `N` — действительный, `C` — отменённый).
- «Было более 2 приёмов» = приёмов **строго больше двух** (от 3-х).
- Исключение в строках 4-6: «кроме Шорстова визитов к другим врачам не было»,
  т.е. отсекаются все пациенты, чьи визиты — **только** к Шорстову
  (не только случай с одним визитом). «Другой врач» — любой `Doctor_ID`,
  кроме 10000040, без исключений. Пациент без визитов (только запись
  на будущее) остаётся в общих сценариях.
- Полного «разделения» строк 1-3 и 4-6 при этом не получается: пациент
  с 3+ визитами к Шорстову **и** визитом к другому врачу подходит под обе строки.
  Поэтому связка по `delivery_id` в блоке повтора обязательна (см. выше).
- «Дата приёма в диапазоне дней назад/вперёд» — по `patients_visits.Visit_date`;
  в прошлом учитываются визиты с `Visit_date <= GETDATE()`.
- Время работы внутри сегмента не ограничивается — его задаёт расписание
  сценария в PR2 (общее окно отправок 09:00–21:59).
- Дедупликация — только по `phonex`. Семейные дубли (родитель + ребёнок)
  намеренно не схлопываются: у каждого свой день рождения.
- **29 февраля.** Пациенты, рождённые 29.02, в невисокосный год
  поздравление не получат. Если нужно 28.02 — заменить условие ДР на:
  ```sql
  AND ( (MONTH(dob) = MONTH(GETDATE()) AND DAY(dob) = DAY(GETDATE()))
     OR (MONTH(dob) = 2 AND DAY(dob) = 29
         AND MONTH(GETDATE()) = 2 AND DAY(GETDATE()) = 28
         AND DAY(EOMONTH(GETDATE())) = 28) )
  ```

## Проверка

1. `SET PARSEONLY ON` + реальный запуск на локальной базе `wellness_new`
   (клиника 2523, та же схема): все 6 файлов — без ошибок.
2. Логика проверена на синтетических пациентах во временной БД
   (`tmp_bd_check`, таблицы `patients` / `patients_visits` / `vmessages` /
   `phonex`): 18 кейсов, все 6 сегментов дали ожидаемые наборы
   (в т.ч. отсев «только Шорстов» с 2 визитами, визит к Рентгену как
   не-«другому» врачу, пациент без визитов с записью на будущее, повтор
   180 дней, `exclude = 1`, телефон не `79%`, дубль в `phonex`). База удалена.

## Не сверено

Файл `doctors.xls` — выгрузка из МИС клиники; локальной базы Imed City нет,
поэтому соответствие `Doctor_ID` (100000xx) значениям `doctors.Doctor_ID`
в боевой базе клиники не проверено. Перед включением сценариев сверить:
```sql
SELECT Doctor_ID, FullName FROM doctors WHERE Doctor_ID IN (10000040, 10000001, 10000038, 10000078, 10000144);
```
Если id в боевой базе другие — заменить их в сегментах (поиск по `10000040` и
списку служебных).
