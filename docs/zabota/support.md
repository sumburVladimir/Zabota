## Структура отдела и линии

Задачи техподдержки ведутся в четырёх **проектах Bitrix24**:

| Проект | Назначение |
|---|---|
| L1 | Задачи 1-й линии (первичный приём, привязки, типовые настройки). |
| 2-я линия | Задачи 2-й линии (настройка сценариев, интеграции, базы, модули). |
| 3-я линия | Повышенная техническая квалификация: кастомные сценарии, нестандартные решения в БД, доработка интеграций. |
| Внутренняя техподдержка | Корпоративные сервисы, доступы, телефония, внутренние IT-вопросы. |

**Роли и графики** (из «Должностные обязанности…» и «Зона ответственности…»):

- **Заместитель руководителя ТП** — операционное управление, загрузка отдела, контроль Scrum Master, приоритеты/риски, качество, аналитика, регламенты. Пн–пт 9:00–18:00 МСК.
- **Специалист 2-й линии** — настройка/корректировка сценариев и сегментов по брифу, расписания, восстановление/перенос БД, установка и настройка ПО, подключение обратной интеграции, диагностика ошибок отправки, установка Модуля Ответов (>5 рабочих мест), квиз-формы, холодная база. Основной состав Пн–пт; дежурный — Сб/Вс 9:00–18:00.
- **Специалист 3-й линии** — кастомные сценарии и отчёты, нестандартные таблицы/функции в БД, восстановление БД, доработка интеграций (кастомные поля/метки/таблицы), обслуживание сервиса BigRep (мониторинг ЛК, балансов, SMS-сервиса Интис).
- **Специалист внутренней ТП** — платежи за IT-инфраструктуру, облачная телефония Mango, администрирование Bitrix24, почтовый сервис, Wazzup24 для продаж, поддержка сотрудников.
- **Scrum Master** — распределение задач, загрузка, сроки, прозрачность.

## Типизация задач

Каждая задача описывается двумя тегами (**«Регламент типизации задач…»**):

> **Primary → Action**

- **Primary** — с чем работаем (объект, продукт, служба, направление).
- **Action** — что с ним делаем.

Если в задаче есть проблема, добавляются ещё два:

> **Primary → Action → Problem Type → Error Source**

- **Problem Type** — что именно произошло.
- **Error Source** — на чьей стороне / из-за чего.

**Полный справочник Primary:**

| Primary | Что это |
|---|---|
| Z.Desktop | Десктопная версия Заботы |
| Z.Cloud | Облачная версия Заботы |
| Сценарии | Сценарии отправок и их настройки |
| Интеграции | Модуль интеграции с МИС |
| МИС | Медицинская информсистема клиента |
| WA / WABA | WhatsApp / WhatsApp Business как канал |
| TG | Telegram как канал |
| MAX | MAX как канал |
| SMS / EMAIL | SMS- и Email-каналы и шлюзы |
| Звонобот | Канал автоматических звонков |
| Producer | Служба отправок |
| МО | Модуль Ответов |
| ОИ | Обратная интеграция с МИС |
| PR2 | Инструмент управления сценариями (не Primary для рабочих задач) |
| SyncApp | Служба обновления и взаимодействия с данными (альтернатива zac) |
| GAPI / WZ24 | Внешние сервисы/подрядчики по каналам |
| messaging.zabota.space / wp.zabota.space | Микросервисы привязок |

**Правила типизации:** Primary — только один; если затронуто несколько, берётся приоритетный. Тег типизации устанавливают **только руководители ТП, Scrum Master и сервисы автопостановки** (например, мониторинг статистики).

## Постановка задач

Источник — «Регламент постановки задач в отдел ТП».

**Способы постановки:**
1. **Автозадача** — создаёт задачу по шаблону и автоподтягивает данные из сделки (доступы, ответственных).
2. **Умный сценарий** — создаёт задачу с автозаполнением; ответственный и соисполнитель заполняются автоматически.
3. **Напрямую в проекте** — вручную, с шаблонами описания.

**Обязательные требования:**
- Задача **без проекта в работу не берётся**.
- Название формулируется **через требуемое действие/результат**, а не через проблему:
  ❌ «Не отправились сообщения» → ✅ «Необходима переотправка сообщений».
- Описывать **проблему и требуемое действие раздельно**, указывать ожидаемый результат.
- **Доступы (логины, пароли, данные подключения) — текстом в задаче**, не скриншотом/фото.
- Для переотправки сообщений: ФИО, номер, код сценария, скриншот из МИС (дата/врач/статус/ФИО), какие сообщения и за какой период.
- Для интеграций/сценариев: бриф, коды сценариев, условия сегментации, данные интеграции, ТЗ для кастомных доработок.
- Для привязок WA/WABA/TG: номер, тип сервиса, чат, тип привязки «Первичная»/«Повторная».

**Жизненный цикл и дедлайны:**
- Оценка задачи — **в течение 1 суток** с момента постановки (в идеале в день постановки).
- После назначения крайнего срока постановщику приходит **уведомление в ЛС**.
- **Возврат** (неполное описание, нет доступа/брифа/ТЗ, неверные данные, не тот проект) → постановщику **2 календарных дня** на исправление; иначе задача закрывается как неактуальная.
- **Отложенные задачи** — обязателен крайний срок; стандартный **14 календарных дней**, затем автозакрытие.
- Отложено из-за разработки → в задаче ТП **обязательно связанная задача разработки**; к её сроку добавляется **+2 дня для ТП** (тестирование/доработки).
- **Тестирование** → постановщик принимает или возвращает в доработку (конкретно, что исправить); фиксируется обратная связь конечного пользователя.
- **Автозакрытие** на стадии тестирования — **14 календарных дней**; после закрытия задача возврату не подлежит (новая проблема = новая задача).

## Сроки и теги срочности (SLA)

Источник — «Регламент установки тегов срочности и сроков…».

Теги срочности ставят **только руководители/замы или Scrum Master**; самостоятельная смена запрещена.

| Тег | Смысл | Срок оценки | Крайний срок |
|---|---|---|---|
| ASAP | Полная остановка/существенное затруднение работы | в день постановки | 1 день |
| Наивысший | Большое число пользователей / критичные процессы | в день постановки | 1–3 дня |
| Высокий | Замедляет, но не прерывает бизнес-процессы | 1 день | 5–6 дней |
| Умеренный | Отдельные аспекты, не влияет на глобальное | 2 дня | 6–7 дней |
| Низкий | Можно делать в свободное время | 2 дня | 7–9 дней |

**Декабрь/январь** — сроки увеличены: Высокий 6–8, Умеренный 9–10, Низкий 10–12 дней.

**Примеры приоритетов:**
- **ASAP** — отказ облачных серверов, сбой микросервисов (web-формы, подтверждения, NPS, квизы, WA/SMS/TG/E-mail), критические ошибки БД.
- **Наивысший** — обновление модулей (МО, Управления, Продюсер, Импортёр) для фикса ошибок, критические правки сценариев/служб, перенос/восстановление ПО по вине поставщика (по вине клиента — приоритет падает до «Высокий»), привязка/перепривязка шлюза WA/SMS.
- **Высокий** — правки сценариев/акций, проверка вспомогательных служб (ZAC), перенос/восстановление из-за поломки сервера клиники.
- **Умеренный** — замечания пользователей, второстепенные функции, правки web-форм, выгрузка данных, кастомизация импорта/БД.
- **Низкий** — минорные обновления, мелкие баги, обновление документации.

**Сроки для клиента:** сообщается актуальный крайний срок из задачи; отдельного внутреннего срока нет.

**Переоценка/увеличение сроков** — по 10 причинам (нет информации, нет доступов, кривое ТЗ, согласование с другими отделами, сложность, внутренние ограничения, внешние факторы, нет обратной связи, задача шире ожиданий, ошибка в данных). Срок меняется только с уведомлением инициатора. Отсчёт — по производственному календарю, выходные/праздники не считаются.

## Каналы и типовые кейсы

### WhatsApp (Wazzup / WABA)

Самый проблемный канал. Причины блокировок: массовые сообщения с мало-уникальным текстом (чаще всего «виноваты» акции), жалобы пациентов.

- **Полная блокировка** — потеря доступа к номеру; восстановление через «Запросить рассмотрение» в приложении, форму на `whatsapp.com/contact/noclient`, дублирование на `accessibility@support.whatsapp.com` / `android@support.whatsapp.com` (с видео установки из GooglePlay/AppStore). Ответ на русском — 1–2 дня.
- **Частичная блокировка** — можно отвечать в существующих чатах, но нельзя писать первым; обычно временная.
- **После разблокировки:** остановить сценарии, выждать 1–2 дня с «прогревом» номера живой перепиской, проверить очередь отправок (Wazzup), восстанавливать объём постепенно (по 3–4 сценария в день); **акции запрещено запускать минимум неделю**.
- **Повторные блокировки** — пересмотреть объём/уникальность, сократить до минимума (только записи и напоминания), при продолжающихся банах — регистрация нового номера и **обязательно смена устройства**.
- **Если не снимается** — предлагать **WABA** (официальный WhatsApp): при блокировке блокируется шаблон, а не весь номер.
- Другие ошибки: «неофициальная версия приложения», «необходимо установить официальное приложение», статус `suspended`, ошибка 486, нестабильность привязки.

### MAX (мессенджер)

Отдельный блок статей: регистрация, установка на ПК, привязка к PR2, безопасный режим, типы блокировок, как снизить риск блокировки, `suspended`-статус, хранение идентификаторов пользователей.

### Telegram / E-Mail / SMS

- Telegram: регистрация ботов и каналов, TG-бот техподдержки (команды/функции), Telegram Personal, боты для каскадов (LKBOT), как избежать блокировки.
- E-Mail: подключение канала, требования к HTML-шаблону писем, смайлы в шаблонах.
- SMS: через Интис Телеком / Интис.

### Инструменты поддержки

Whatsapp Accounts Tool, NPS URL Tool, Quiz Copy Tool, PTRR Tool, Breef Text Sync (BTS), конструктор сегментов, планировщик рассылок (новое расписание), автозадачи, «светофор сценариев».

## Интеграция с МИС

Источник — «МИС с которыми интегрируется Zabota 2.0». Два типа подключения:

- **API-интеграция** — для облачных МИС или при наличии внешнего API; обмен по защищённым каналам, без прямого доступа к БД клиента.
- **Локальная интеграция** — прямое подключение к СУБД МИС (on-premise), в режиме «только чтение».

## Установка и обслуживание

- Программно-аппаратные требования и состав устанавливаемого ПО.
- Установка дистрибутива Zabota 2.0 Desktop, ручная установка Облака.
- Обновление PR2 (локально и на облаке), проверка/обновление продюсера вручную.
- Перенос БД на другой сервер, резервное копирование (Облако CBD1-9), подключение холодной базы.
- Мультифилиальная версия PR2, OpenVPN/Wireguard для облака, VPN-сервисы для модулей.
- Пользовательские модули, каскадная версия PR2 (чек-лист проверки после перевода).
- Технические меры информационной безопасности, облачное пространство Google Диск.

## Пробелы и противоречия

- Часть статей — «скелеты» (только заголовок, без текста), особенно в подразделах-оглавлениях.
- Сводного регламента **1-й линии** в этом пространстве нет — только 2-я и 3-я; L1-регламенты лежат в пространстве «Разработка» (проект Cloud) и «Внутренняя ТП».
- Точных цифр SLA по приёму звонков/чатов (время ответа) в статьях нет — сроки привязаны к тегам срочности задач.
- По Telegram-каналу (личному/Personal) описаний меньше, чем по WhatsApp и MAX.
