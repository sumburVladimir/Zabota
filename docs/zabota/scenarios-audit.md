# Аудит сценариев рассылок по брифу (памятки и приглашения)

Как проверять, что настроенные в базе сценарии соответствуют брифу клиники,
и как аккуратно править найденные расхождения.

Устройство таблиц — [producer.md](producer.md). Пример полного прохода —
`docs/zabota/clients/2523/tasks/memos-group-check.md` и `invites-check.md`.

## 1. Что запросить у клиники

Минимум (CSV/XLS, UTF-8):

| Что | Зачем |
|---|---|
| `procgroups` + `procedurex` + `procedures` | состав групп услуг |
| `deliveries` | сценарии: код, активность, каналы, интервалы |
| `deliv_conditions` | сегменты (`Expression`, `Condition_Type`, `saved_code`) |
| `deliv_params` | фактические `:IGROUP` / `:GROUPID` / `:DID` / `:IPAT` |
| `doctors` | сверка списков «нет записи на будущее» |
| `delivery_schedule_trigger` | расписание (дни, окно, период) — если важны интервалы |

Если чего-то не хватает, не додумывать: связь «сценарий ↔ условие» без
`deliv_params` не определить.

## 2. Сверка услуг брифа с базой

**Сначала выяснить, как в этой базе задан набор услуг** — общего стандарта нет:

| Способ | Признак | Где смотреть |
|---|---|---|
| Группой процедур | в сегменте `procgroups`/`procedurex` и параметр `:IGROUP`/`:GROUPID` | `deliv_params` |
| Перечислением ID | `p.Procedure_id IN (123, 456, ...)` | текст `Expression` |
| Не по услугам | условия по врачам, суммам, визитам | текст `Expression` |

Группы процедур — удобная, но необязательная механика (пример — клиника 2523);
в большинстве баз услуги перечисляются прямо в сегменте.

Дальше, для выбранного способа:

1. В брифе услуги записаны как `КодМКБ + «Категория / подкатегория»`
   (`A22.01.004Лазерная коагуляция телеангиоэктазий / QuadroStarPRO лицо`).
2. В `procedures` кода нет, название в `Descr` (`Name` — GUID из МИС).
3. Нормализация: нижний регистр, `ё → е`, убрать `«»"'`, схлопнуть пунктуацию
   в пробелы, обрезать звёздочки.
4. Совпадение: точное после нормализации; fuzzy ≥ 0.97 — считать совпадением;
   0.88–0.97 — вывести на ручную проверку (иначе «Холи Ленд лечебная чистка»
   схлопнется с «…чистка Экспресс»); ниже — «нет в базе».
5. Услуги брифа делятся на блоки: «была получена услуга N дней назад» и
   «исключить получение 0–N-1 дней» — это разные списки, при парсинге их нельзя
   смешивать (иначе счёт удваивается).

Готовый скрипт: `tools/brief_group_match.py`.
Режимы: `--list` (посмотреть услуги по секциям брифа), `--find-only` (сопоставить
со справочником и выдать `proc_id` — для баз, где услуги перечисляются в сегменте),
`--check КОД=GROUP_ID` (сравнить с группой — для баз с группами процедур).

## 3. Чек-лист проверки сценария

| № | Проверка | Как смотреть |
|---|---|---|
| 1 | Сценарий активен и не удалён | `dactive = 1`, `deleted = 0` (у дублей бывает `PW4*` и `PW4`) |
| 2 | Срок после услуги совпадает с брифом | `DATEDIFF(...) = N` в `Expression` |
| 3 | Исключение «свежих» услуг | должно быть `NOT EXISTS`, а не `IN` |
| 4 | Ограничение повтора | `DATEDIFF(DAY, do.Created, GETDATE()) <= N`, дата обязательна |
| 5 | Возраст | `patients.age >= 18` |
| 6 | «Нет записи на будущее» | `NOT EXISTS (patients_visits ... Visit_state='N')` + список врачей |
| 7 | Список врачей | сверить ID с `doctors` (бывают дубли ФИО, уволенные, «НЕ ИСПОЛЬЗОВАТЬ») |
| 8 | Услуги | набор брифа покрыт: группой из `:IGROUP`/`:GROUPID` **или** перечислением `Procedure_id` в сегменте |
| 9 | Ограничение прогона | `top :IPAT`, а не `TOP 3` |
| 10 | Каналы | WA / TG / MAX — по карточке сценария в PR2 (в выгрузке флаги могут быть пустыми) |
| 11 | Расписание | `delivery_schedule_trigger`: дни, окно, период |

## 4. Типовые баги (найдены в реальных базах)

1. `SELECT TOP 3` вместо `SELECT top :IPAT` — обрабатывается 3 пациента за прогон.
2. Блок «исключить получение услуг 0–N дней» реализован через
   `AND patients.patient_id IN (...)` вместо `NOT EXISTS` — свежие услуги не
   исключают пациента, а требуются. Встречается во всех SQL-сегментах подряд.
3. `do.Delivery_id IN (:DID, 542)` без даты — повтор «навсегда».
4. Набор услуг покрывает не весь бриф (чистки без пилингов) или шире брифа
   (зоны тела в приглашении «на лицо») — смотреть группу либо список `Procedure_id`.
5. `= :IGROUP` при том, что услуг две темы → нужен `IN` + список групп,
   либо одна группа-объединение (надёжнее). Актуально только там, где группы есть.
6. `procedurex.exclude = 1` не фильтрует сегмент, пока в тексте нет
   `AND ISNULL(p.exclude, 0) = 0` (тоже только для баз с группами).

## 5. Как править

1. **Бэкап затронутых строк**:
   `SELECT * INTO dbo.<table>_bak_YYYYMMDD FROM dbo.<table> WHERE <фильтр>;`
2. Для `Condition_Type = 1` — править `Expression`; для `2` — только через PR2
   (иначе конструктор перезапишет).
3. Наполнение групп — только если механика групп используется:
   `INSERT INTO procedurex (code, exclude, proc_id, group_id)`
   с `WHERE NOT EXISTS` (идемпотентно) и сверкой `@@ROWCOUNT` с ожидаемым числом.
   Иначе — правка списка `Procedure_id` в тексте сегмента.
4. Каждый блок — в своей транзакции; несовпадение количества → `ROLLBACK`.
5. Не трогать существующие группы, если они используются другими сценариями —
   проверить `deliv_params` (`Value` = id группы) и тексты всех условий.
6. После правки — контрольный запрос: количество услуг в группе/списке и ключевые
   фрагменты `Expression` (наличие `IN`, `NOT EXISTS`, нужных id).

### 5.1 Логика условий: по умолчанию `AND`, `OR` — только по брифу

Все условия брифа соединяются через `AND`. `OR` ставится **только** там, где
в брифе явно написано «ИЛИ» (составной запрос, например: «были визиты у
врачей **ИЛИ** была получена услуга»). Если бриф перечисляет пункты списком
без союза — это `AND`.

Если сегмент отбирает подозрительно мало пациентов (2–3), нельзя «расширять»
его своим `OR`. Сначала уточнить у автора брифа, чем считать условие
(визит или оказанная услуга, какие именно дни, какой набор услуг), и только
потом менять SQL.

## 6. Проверка SQL до запуска на рабочей базе

1. `SET PARSEONLY ON` — ловит синтаксис.
2. **Реальный прогон на временной БД**: `CREATE DATABASE tmp_...`, создать копии
   таблиц, загрузить данные из выгрузок, выполнить скрипт, проверить, `DROP`.
   Ловит то, что не видит `PARSEONLY` (несуществующие колонки, логику).
3. Помнить: `PRINT` не принимает подзапрос (считать в переменную), `GO` сбрасывает
   переменные (объявлять в каждом батче).
4. Выборки условий прогонять, подставив параметры вручную (`:IGROUP` → `28`,
   `:DID` → `552`), и смотреть, что запрос вообще исполняется.

## 7. Особенности выгрузок

- Кириллица в `varchar` при collation `Cyrillic_General_CI_AS` — сохраняется;
  в скриптах писать `N'...'`.
- Python → PowerShell ломает кириллицу в консоли: результат писать в файл UTF-8
  и читать файлом, а не печатать.
- `pandas.read_excel` подхватывает `.xls` от МИС/SSMS без конвертации.
